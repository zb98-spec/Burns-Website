# Wine Project Rebuild — Development Plan

Scope: `app/blueprints/wine_cellar/*` only. No other blueprint touched.

## Current state (for reference)

- One blueprint, two concepts already: `Bottle` (cellar inventory) and
  `TastingHistory` (drink log), `bottle_id` on `TastingHistory` is already
  nullable with a snapshot of name/producer/vintage — so "log a tasting
  without a cellar entry" is already half-true at the DB level, just not
  exposed anywhere.
- 4 templates: `index.html` (cellar table), `form.html` (add/edit bottle),
  `drink.html` (log a tasting from a bottle), `history.html` (flat table of
  past tastings, single `rating` int column).
- Deployed on Cloud Run (scales to zero, ephemeral container disk) — **local
  file storage for uploaded images will not survive a redeploy or scale-down
  event.** Images must go somewhere durable: Neon Postgres (bytea column) or
  a bucket. No bucket is wired up today, so storing image bytes in Postgres
  is the lazy, infra-free option and is what this plan uses.

## Decisions

| Question | Decision | Why |
|---|---|---|
| Where do tasting images live? | `bytea` column on `TastingHistory` (or a child table), served via a `/tastings/<id>/image` route | No object storage exists in this project yet; Postgres already does, and images here are small/occasional, not a media library |
| How are multi-person scores modeled? | New `TastingScore` table (`tasting_id`, `taster_name`, `score`), replaces the single `rating` int on `TastingHistory` | Displayed score = average of these; per-person breakdown = these rows |
| How do you add N score rows in one form? | Minimal vanilla JS "add another score" button | Matches existing stack decision (server-rendered Jinja + minimal vanilla JS, no framework) |
| Hover-to-reveal score breakdown | CSS-only `:hover` popover on the tasting card | No JS needed for this part |
| Two pages | `wine_cellar.index` (Cellar) stays; `wine_cellar.history` becomes the Tasting page, rebuilt as cards | Reuses existing routes/URLs, avoids a new blueprint |

## Phases

Each phase is independently completable and testable. Phases 1–2 are
prerequisites for everything else; 3–6 can run in parallel (e.g. as
separate subagents) once 1–2 land, since they touch different routes/files.

### Phase 1 — Nav cleanup (small, do first, unblocks nothing but is trivial)
- `app/templates/base.html`: style the existing "Burns Dashboard" header
  link as a `btn` so it reads as a top-bar button.
- Remove the in-page `<p><a href="{{ url_for('core.index') }}">← Back to
  dashboard</a></p>` line from `wine_cellar/index.html`.
- Leave the "← Back to wine cellar" links on `form.html`/`drink.html` alone
  — those are page-to-page nav within the project, not the dashboard link.

### Phase 2 — Schema migration
- `models.py`:
  - Add `TastingScore(id, tasting_id FK→wine_tasting_history, taster_name, score)`.
  - Add `image` (`LargeBinary`) + `image_mimetype` (`String`) to `TastingHistory`.
  - Drop `TastingHistory.rating` (superseded by `TastingScore`; add a
    property `average_score` that computes from `scores` in Python instead
    of storing a derived column).
- Generate + review a Flask-Migrate migration (`flask db migrate`, hand-check
  the autogenerated script per this repo's existing migration convention).

### Phase 3 — Standalone tasting entry (decouple from cellar)
- New route `wine_cellar_bp.route("/tastings/add", methods=["GET", "POST"])`:
  same form as `drink.html` but wine name/producer/vintage are free-text
  fields instead of coming from a `Bottle`, `bottle_id` stays `None`, no
  quantity decrement.
- Keep `/<bottle_id>/drink` as-is for the cellar-linked path (it already
  writes the same `TastingHistory` snapshot shape).

### Phase 4 — Score rows in the tasting form
- Add taster-name + score fields to `drink.html` and the new
  `tastings/add.html`, with a small vanilla-JS "+ Add another score" button
  that clones a row template (no framework).
- Route handlers (`drink`, new `add` tasting route) parse repeated
  `taster_name[]` / `score[]` form fields into `TastingScore` rows, skipping
  blank rows.

### Phase 5 — Image upload
- Add `<input type="file" accept="image/*" capture="environment">` to both
  tasting forms (the `capture` attribute opens the phone camera directly).
- On POST, read `request.files["image"]`, store `.read()` bytes +
  `.mimetype` on the `TastingHistory` row (skip if empty).
- New route `wine_cellar_bp.route("/tastings/<id>/image")` streaming the
  bytes back with the stored mimetype (404 if none).

### Phase 6 — Tasting page rebuild (cards + hover)
- Rename `history.html`'s purpose (keep the `wine_cellar.history` endpoint
  name to avoid churn, or rename to `wine_cellar.tastings` — pick one and
  update the nav links in Phase 1/2) to a card grid:
  - Each card: wine name/producer/vintage, date, thumbnail if an image
    exists, average score badge.
  - `:hover`/`:focus-within` on the card reveals a small popover listing
    each `taster_name: score`.
  - "Add a tasting" button on this page linking to the Phase 3 route.
- Update `index.html` (Cellar) page-header actions to link to the renamed
  Tasting page, and add matching nav the other direction.

### Phase 7 — Tests + docs
- Extend `tests/test_wine_cellar_unit.py` / `_integration.py` for: standalone
  tasting creation, score average calculation, image upload/serve round
  trip, nav link removal.
- Update `DEVELOPMENT_PLAN.md`'s Wine Cellar section and `TESTING.md` per
  this repo's existing convention of keeping those current.

## Suggested execution order

1. Phase 1 (trivial, do it directly)
2. Phase 2 (schema — blocks 3/4/5/6, do it directly since migrations need
   one careful pass, not parallel edits)
3. Phases 3, 4, 5, 6 — four independent subagents, one per phase, since
   after Phase 2 they touch disjoint concerns (routes for 3/4/5 can even
   land in one pass since they're all in `routes.py`, but 6 is templates
   only and can run in parallel with them)
4. Phase 7 last, after everything else is merged, to test the real behavior
